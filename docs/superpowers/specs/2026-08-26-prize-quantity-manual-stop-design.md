# 奖品数量与手动停止抽奖设计

**日期：** 2026-08-26  
**状态：** 口头设计已逐段确认；书面规格待审阅  
**范围：** 奖品增加数量，同一奖可连抽多次，抽满后才进中奖屏；开奖改为「开始滚动、点停再定人」；内定改为按抽次槽位。

---

## 1. 背景与目标

### 1.1 现状

- 技术栈不变：Vite + React（`client/`）+ Express（`server/`）+ JSON 文件（`data/`）。
- 每个奖品只能开奖一次：`winners` 中出现该 `prizeId` 即视为已抽。
- 点「开始抽奖」立即 `POST /api/draw`，前端滚动减速停到已抽出的人；停稳高亮 3 秒后自动进第四屏。
- 第四屏上方只公示本轮一人；下方为已中奖总名单。
- `/admin` 每奖只能内定一人（`presets` 为 `prizeId → participantId`）。
- 同一人不可重复中奖；内定优先级最高，可覆盖该规则。

### 1.2 已确认需求

| 维度 | 选择 |
|------|------|
| 数量含义 | 同一奖品可抽次数；例如 3 即抽出 3 个不同的人 |
| 未抽满时 | 停在抽奖屏，主持人再点「开始抽奖」 |
| 抽满后 | 最后一次高亮 3 秒结束，自动进第四屏 |
| 开奖时机 | 点「开始」只滚动；点「停」才调用后台开奖，再减速停到系统抽出的人 |
| 第四屏 | 本奖全部中奖人一起放大；下方仍是总名单 |
| 内定 | 最多 N 人，按第 1 次…第 N 次槽位依次必中；空槽随机 |
| 每次抽出后 | 都高亮停留 3 秒（含中间几次） |
| 实现策略 | 在现有模型上加数量和延后开奖（方案 1），不新增一轮状态机 |

### 1.3 目标

- 一份奖可以发给多个人，现场连抽，抽满再一次公示。
- 主持人用「停」掌控开奖瞬间，观众仍看到减速停名；内定与随机规则仍由后台决定。
- 数量为 1 时，除「先滚后停」外，公示形态与现在基本相同。

### 1.4 非目标

- 一次滚动同时抽出多人。
- 点停定格当时屏幕上的名字（不采用客户端定人）。
- 为「第几次」新增 session 字段或服务端抽奖状态机。
- 多设备逐帧对齐滚动。
- 把数量拆成多条内部奖品。
- 音效、粒子、主题皮肤、公网部署。
- 改姓名录入、四屏顺序、控制条隐藏方式。

---

## 2. 整体流程

四屏顺序不变：参与 → 奖品 → 抽奖 → 中奖。一次只显示一屏。

同一奖品（数量 N）现场路径：

1. 选中该奖，停在奖品屏；可见进度（例如「3 份 · 已抽 0/3」）。
2. 点「开始抽奖」：进入抽奖屏并滚动。此时不写中奖记录。
3. 点「停」：后台开出第 k 个人，滚动减速停到该人并高亮。
4. 高亮停留 3000ms（不含减速）。未满 N：仍停在抽奖屏，按钮恢复为「开始抽奖」。
5. 重复 2–4，直到第 N 次。
6. 第 N 次的 3000ms 结束后自动进入第四屏，一次放大本奖全部中奖人。

换下一个奖品：从奖品屏再开始。已抽完的奖选中后进入第四屏，展示该奖全部中奖人。

控制条仍可手动切屏、选奖、隐藏。滚动、减速或 3 秒停留期间「开始抽奖」与「停」均不可用。若在这些期间手动切到其他屏：取消尚未执行的自动跳转（含未启动或进行中的 3 秒定时器）；若尚未点停，不产生中奖记录。

## 3. 数据模型

存储仍是现有 JSON 文件，不新增文件种类。剩余次数由「该奖 `winners` 条数」与 `quantity` 比较得出，不写入 session。

### 3.1 奖品

`Prize` 增加：

- `quantity`：整数，≥ 1，表示该奖可抽次数。

读入时若缺省该字段，视为 `1`。`PUT /api/prizes` 必须带合法 `quantity`，写入时不再省略。

已抽出人数为 X（`winners` 中该 `prizeId` 的条数）时，新的 `quantity` 不得小于 X；否则拒绝保存。

### 3.2 中奖记录

`WinnerRecord` 仍为 `{ prizeId, participantId, at }`。同一 `prizeId` 允许多条。同一 `participantId` 在整个 `winners` 中至多出现一次（内定开奖除外，规则与现在相同）。

该奖已抽完 ⇔ 该 `prizeId` 的记录条数 ≥ `quantity`。

### 3.3 内定

由 `Record<prizeId, participantId>` 改为 `Record<prizeId, Array<string | null>>`。

- 数组长度必须等于该奖当前 `quantity`。
- 下标 `i` 对应第 `i+1` 次抽取（第 1 次下标 0）。
- 非空字符串：该次必中此人。
- `null`：该次从当时可抽池随机。

读入兼容：若值为字符串，视为只填第 1 槽，其余补 `null` 直到长度等于 `quantity`。若数组短于 `quantity`，右侧补 `null`；长于 `quantity` 的多余槽丢弃（仅当数量合法缩小之后发生）。

同一奖品的非空槽不得出现重复的 `participantId`。

数量变大：在现有槽后补 `null`。数量变小（且不低于已抽人数）：裁掉末尾槽。`PUT /api/prizes` 在数量合法变更时同步改写该奖的内定数组长度，避免槽数与 `quantity` 不一致。某奖在 `presets` 中无键，视为全部空槽。

`DELETE /api/presets/:prizeId` 仍删除该奖全部内定。

## 4. 抽奖节奏（大屏）

### 4.1 开始滚动

大屏不读取内定名单。`GET /api/public/view` 增加布尔字段 `canDraw`：当前奖存在、未抽完，且（本槽有非空内定 **或** 可抽池非空）时为 `true`。不暴露内定是谁。

点「开始抽奖」时校验：

- 无当前奖品 → 不滚动，提示与现在相同。
- 该奖已抽完 → 不滚动，提示「该奖品已抽完」。
- `canDraw === false` → 不滚动，提示「没有可抽奖用户」。

通过后：会话切到抽奖屏、`drawPhase: "rolling"`；用当时名单做滚动快照；**不调用** `POST /api/draw`。

滚动期间控制条主按钮为「停」。刷新页面或在点停前切走，等于放弃这一次滚动，次数不增加。

### 4.2 点停开奖

点「停」才 `POST /api/draw`。服务端：

1. 仍要求已选当前奖且奖品存在。
2. `drawnCountBefore` = 该奖已有中奖条数。若 `drawnCountBefore >= quantity`，`400`，消息「该奖品已抽完」。
3. 取内定槽 `slots[drawnCountBefore]`。非空则必中该人（优先级与现在相同，可覆盖不可重复中奖）。
4. 空槽则在可抽池中均匀随机；池空则 `400`，「没有可抽奖用户」。
5. 追加一条 `WinnerRecord`；`drawPhase` 为 `revealed`；`publicScreen` 保持 `draw`；更新 `lastWinnerParticipantId` / `lastWinnerPrizeId` 为本条结果。

成功返回在现有字段上增加：

- `drawnCount`：本奖当前中奖条数（含刚刚这条）
- `quantity`：该奖数量
- `prizeComplete`：`drawnCount >= quantity`

前端用返回的中奖姓名减速停稳并高亮。点停后接口失败：停止滚动、提示错误、不计数，可再次点「开始抽奖」。

减速或 3 秒停留期间主按钮禁用，文案「抽奖中…」。

### 4.3 停稳停留与切屏

停稳并选中后停留 **3000ms**，不含减速。停留期间会话保持抽奖屏。

3000ms 到点后：

- `prizeComplete === false`：留在抽奖屏，主按钮恢复「开始抽奖」，可抽下一人。
- `prizeComplete === true`：自动 `publicScreen: "winner"`。

滚动、减速或停留期间主持人手动切屏：取消尚未执行的自动跳转；若尚未点停，忽略之后的停稳回调，不自动进中奖屏。已点停则中奖记录已持久化，只是不自动切第四屏。

滚动动画只在点「开始」的那一台播放，不做多设备逐帧对齐。

### 4.4 控制条奖品下拉与按钮

- 未抽满且不在滚动/减速/停留：主按钮「开始抽奖」。
- 滚动等待点停：主按钮「停」。
- 减速或 3 秒停留：禁用，「抽奖中…」。
- 已抽完：禁用，「已抽取」。

下拉：

- 已抽完：`{名称}（已抽）`。
- 数量为 1 且未抽：只显示名称（与现在相同）。
- 数量大于 1 且未抽完：`{名称}（已抽 a/b）`，含 `0/3`。

选中已抽完的奖：切到中奖屏。选中未抽完的奖：切到奖品屏。

## 5. 各屏与管理页

### 5.1 奖品屏

当前奖名称、图片保留。增加一行进度：`{quantity} 份 · 已抽 {drawnCount}/{quantity}`。不放中奖名单、不开抽、不放停按钮。

### 5.2 中奖屏

上方：奖品名与图 + **当前选中奖品的全部中奖人**，按抽出顺序一起放大。数量为 1 时仍是一个大字姓名。

下方：已中奖总名单，按 `winners` 数组顺序（含本奖全部人次）。每行：`奖品名 — 中奖人`。同一奖品占多行。

名单数据仍由 `public/view` 的 `winners` + `prizes` + `participants` 在前端拼接，不新开列表接口。第四屏展示的「本奖中奖人」按 `currentPrizeId` 过滤，不用 `lastWinner` 代替整奖名单。

### 5.3 管理页

奖品每行增加「数量」数字输入，最小 1，随奖品列表一并 `PUT /api/prizes`。

内定区：每个奖按数量展开「第 1 次」…「第 N 次」下拉，可空（未内定）。任一槽变更即提交该奖完整槽数组。已中奖记录列表按时间列出全部人次。清空中奖记录、清空参与者行为不变；清空中奖后 `quantity` 与内定槽保留，可按同一数量重抽。

### 5.4 参与屏

不改。已中奖者仍可改名、不可删除；不进入后续可抽池（内定当次除外）。

## 6. 接口

### 6.1 `PUT /api/prizes`

在现有校验上增加：每项 `quantity` 为 ≥1 的有限整数。任一奖品新数量小于该奖已抽出人数则整单拒绝，`400`，消息说明已抽出人数。成功写入的每条奖品都含 `quantity`。数量相对上次有增减时，按 3.3 同步该奖内定数组长度。

### 6.2 `GET /api/prizes` 与 `public/view`

返回的奖品对象带 `quantity`（读入缺省时已补为 1）。`GET /api/public/view` 增加 `canDraw`（见 4.1），其余顶层字段不变。

### 6.3 `GET /api/presets`

管理口令。返回 `Record<string, Array<string | null>>`。读入时做第 3.3 节兼容。

### 6.4 `PUT /api/presets/:prizeId`

管理口令。请求体 `{ slots: Array<string | null> }`。

- 奖品不存在：`404`。
- `slots.length` 必须等于该奖 `quantity`：否则 `400`。
- 空字符串与 `null` 同等视为空槽，写入为 `null`。
- 每个非空元素必须是已存在的参与者 `id`：否则 `404`，「用户不存在」。
- 非空 `id` 在数组内重复：`400`，消息「同一奖品不能重复内定同一人」。
- 成功：`200`，返回 `{ prizeId, slots }`。

不再接受仅含 `participantId` 的旧请求体。

### 6.5 `DELETE /api/presets/:prizeId`

不变：删除该奖全部槽。

### 6.6 `POST /api/draw`

见 4.2。错误消息：「未选择当前奖品，无法开奖」「当前奖品不存在」「该奖品已抽完」「没有可抽奖用户」「开奖失败」。不再使用「该奖品已开奖」。

### 6.7 保持不变

参与者增删改、session 字段集合、清空中奖、清空参与者。`GET /api/public/view` 仍返回现有顶层字段；新增 `canDraw`；嵌套的 `Prize` 增加 `quantity`；`winners` 本就可多条。

## 7. 组件改动（最小集合）

| 位置 | 改动 |
|------|------|
| `server` 类型与奖品校验 | `Prize.quantity`；读入缺省为 1 |
| `POST /api/draw` | 按已抽次数选内定槽；允许同一奖多条；返回 `drawnCount` / `quantity` / `prizeComplete` |
| `presets` 读写与路由 | 槽数组；兼容旧字符串 |
| `HostControlBar` | 开始 / 停 / 抽奖中 / 已抽取；下拉显示 a/b |
| `PublicStage` | 开始不调开奖；点停才开奖；用 `canDraw` 拦截无法开的开始；按 `prizeComplete` 决定 3 秒后是否进第四屏；选奖按是否抽完切 winner 或 prize |
| `PrizeScreen` | 进度文案 |
| `WinnerScreen` | 本奖中奖人列表（多人一起放大） |
| `AdminPage` | 数量输入；N 个内定下拉 |
| 前端 `Prize` / `DrawResult` 类型 | 与接口对齐 |
| README | 数量、停按钮、抽满再公示 |

不改：随机函数 `resolveWinner` 的核心（仍是内定优先，否则均匀随机）、资格过滤 `listEligible`、姓名录入、四屏枚举与默认顺序。

## 8. 错误处理

| 情况 | 行为 |
|------|------|
| 数量不是 ≥1 的整数 | 管理页不保存；`PUT /api/prizes` 400 |
| 数量小于已抽出人数 | 不保存；400，提示已抽出人数 |
| 同一奖内定重复的人 | 不保存；400 |
| 内定指向不存在的参与者 | 404 |
| 无当前奖 / 已抽完 / `canDraw === false` | 不进入滚动；对应中文提示 |
| 滚动中未点停就切屏或刷新 | 不写中奖记录 |
| 滚动 / 减速 / 3 秒停留中再点开始或停 | 忽略 |
| 点停时开奖接口失败 | 停止滚动，提示错误，该次不计数，可再开始 |
| 保存或网络失败 | 显示错误，界面不假装成功 |

## 9. 测试

**后端：** 数量 3 可连开 3 次，第 4 次失败。缺 `quantity` 的旧奖品按 1 且只能抽 1 次。第 1、3 槽有内定、第 2 槽为空时，三次结果依次为内定甲、随机可抽者、内定乙。同一奖重复内定同一人失败。数量改为小于已抽人数失败。可抽池为空但本槽有内定时 `canDraw` 为 true 且点停仍能开出内定。原有「非内定不可重复中奖」、清空中奖后可再抽、内定可覆盖已中奖，仍通过。

**前端：** 点开始不请求 `/api/draw`；点停才请求。数量 3 时前两次停留结束后仍在抽奖屏；第三次停留结束后进中奖屏。中奖屏渲染本奖全部姓名。数量 1 时上方仍是一个大字姓名。3 秒用假计时器，不等真实滚动时长。

**手工：** `/admin` 设某奖数量 3，填两个内定槽 → 大屏开始/停三次 → 前两次留在抽奖屏，第三次进第四屏且三人一起公示；下拉在未满时显示已抽 a/3。

**不测：** 多浏览器同一帧对齐、音效、真扫码、公网部署。

## 10. 验收标准

- [ ] `/admin` 可为奖品设置数量（≥1）；旧数据无数量时按 1 工作。
- [ ] 数量为 N 时可对该奖成功开奖 N 次，第 N+1 次被拒绝。
- [ ] 点「开始抽奖」只滚动；点「停」后才产生中奖记录并减速停到后台抽出的人。
- [ ] 每次抽出后高亮停留 3 秒；未抽满不自动进第四屏；抽满后 3 秒自动进第四屏。
- [ ] 第四屏上方为本奖全部中奖人（按抽出顺序），下方为含本奖在内的总名单。
- [ ] 内定最多 N 槽，按抽次消耗；空槽随机；同一奖不能重复内定同一人。
- [ ] 控制条在滚动中显示「停」；已抽完显示「已抽取」；数量大于 1 且未抽完时下拉为「已抽 a/b」。
- [ ] 滚动或停留中手动切屏不会再自动跳到中奖屏；未点停则无新中奖记录。
- [ ] 同一人不可重复中奖（内定当次除外）；姓名录入与四屏顺序不变。
- [ ] README 与上述现场操作一致。
